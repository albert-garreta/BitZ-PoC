# Ryzen 9950X3D arithmetic campaign

This extends the existing paired regression harness for the current Ryzen 9
9950X3D. It does not select production kernels automatically. Existing ARM
manifests and historical results are retained.

## Coverage

`x86_manifest.py` is the executable coverage specification. The native profile
with streaming has 39 distinct families, 385 operation/size cases and 1,286 variant cases.
It covers GF products/chains, independent and repeated squares, inverse, XOR,
unreduced products, reduction, dots, fixed multiplication, preparation and
butterflies; raw Montgomery multiply/add/sub/chains, field/native/Boolean MACs,
both reducer scales and context setup; 1/2/4/9-limb wrapping integer arithmetic,
signed16 and full-width/carry-heavy MACs; public 4/9-limb wide products with both
prepared and one-shot APIs; and signed 2/4/9-limb projection.

The consumer matrix adds production-versus-candidate GF folds, single/two-pair
rounds, fused fold/round, fold cascades, raw Montgomery folds, and all seven
complete NTT shapes. The integer-focus winners and retained alternatives are
included, rather than selecting the old nine-limb prototype.

Array sizes are 16, 1,024, 65,536, and 1,048,576 where applicable. Short public
batch lengths, inversion sizes, reducer accumulation counts, integer widths,
and projection sizes are explicitly enumerated in the manifest. Streaming
cases choose a power-of-two length with at least 32*n actively traversed bytes
strictly greater than twice the selected cache group's L3. Other candidates'
resident buffers do not count toward that requirement.

The `q100` fixture retains its historical ID and value 2^100+277 (actually
101 bits); the other fixture is 2^128-159. These are odd-modulus arithmetic
fixtures; no primality assumption is needed for the Montgomery comparisons.
Product accumulators reduce S*R^-1 mod q; native/Boolean accumulators reduce
T mod q, with R=2^128. Projection returns the canonical signed remainder.

### Mathematical workloads

GF arithmetic below uses $\mathbb F_2[X]/(X^{128}+X^7+X^2+X+1)$;
$\oplus$ denotes addition. For Montgomery arithmetic, $\bar a=aR\bmod q$
and $\bar a\odot\bar b=\bar a\bar bR^{-1}\bmod q$, with $R=2^{128}$.
$L$ is the integer limb count. Batch operations evaluate the expression for
every input index; dependency chains feed each result into the next operation.

| Families | Expression |
|---|---|
| `x86_products`, `x86_chain` | $c_i=a_i b_i$; $s_{i+1}=s_i b_i$ |
| `x86_xor`, `x86_square`, `x86_inverse` | $c_i=a_i\oplus b_i$; $c_i=a_i^2$; $c_i=a_i^{-1}$ for $a_i\ne0$ |
| `x86_square_chain` | $c_i=a_i^{2^k}$ |
| `x86_wide`, `x86_reduce` | $W_i=A_i(X)B_i(X)$ without reduction; $c_i=W_i\bmod f(X)$ |
| `x86_dot` | $s=\bigoplus_i a_i b_i=\operatorname{reduce}(\bigoplus_i W_i)$ |
| `x86_fixed`, `x86_fixed_prepare` | $c_i=a_i\tau$; $T=\operatorname{Prepare}(\tau)$ |
| `x86_butterfly` | $u_i=a_i\oplus\tau b_i$, $v_i=b_i\oplus u_i$ |
| `prime_add`, `prime_sub`, `prime_mul` | $\bar c_i=(\bar a_i\pm\bar b_i)\bmod q$; $\bar c_i=\bar a_i\odot\bar b_i$ |
| `prime_chain`, `prime_dot` | $s_{i+1}=s_i\odot\bar b_i$; $s=R^{-1}\sum_i\bar a_i\bar b_i\bmod q$ |
| `prime_linear`, `prime_bits` | $s=\sum_i\bar a_i u_i\bmod q$, with $u_i$ a native word or a Boolean |
| `prime_reduce_product`, `prime_reduce_product_inputs` | $s=SR^{-1}\bmod q$, $S=\sum_i\bar a_i\bar b_i$ |
| `prime_reduce_linear`, `prime_reduce_linear_inputs` | $s=T\bmod q$, $T=\sum_i\bar a_i u_i$ |
| `prime_setup` | $C=\operatorname{MontCtx}(q)$ |
| `integer_add`, `integer_sub`, `integer_mul` | $c_i=(a_i\pm b_i)\bmod2^{64L}$; $c_i=a_ib_i\bmod2^{64L}$ |
| `integer_mac`, `integer_full_mac`, `two_limb_mac` | $s=\sum_i a_i b_i\bmod2^{64L}$; signed16 fixtures also have an exact, non-overflowing signed interpretation |
| `bounded_product` | $c_i=a_i b_i$ exactly, with public active-limb bounds 4 or 9 and an 18-limb output |
| `projection` | $r_i=x_i\bmod q\in[0,q)$, interpreting $x_i$ as a signed integer |
| `gf_fold`, `prime_fold` | $v'_i=v_{2i}+\rho(v_{2i+1}-v_{2i})$ in the respective arithmetic domain |
| `gf_fold_cascade` | $v^{(j+1)}_i=v^{(j)}_{2i}+\rho(v^{(j)}_{2i+1}-v^{(j)}_{2i})$ until one value remains |
| `gf_round_single` | $C_0=\sum_i w_i l_{2i}r_{2i}$, $C_2=\sum_i w_i(l_{2i+1}-l_{2i})(r_{2i+1}-r_{2i})$, $C_1=\sum_iw_i l_{2i+1}r_{2i+1}-C_0-C_2$ |
| `gf_round_two` | $C=C^{(1)}+C^{(2)}$, summing the coefficient triples for two pairs |
| `gf_fold_round` | $l'=F_\rho(l)$, $r'=F_\rho(r)$, $C=\operatorname{Round}(l',r',w)$, where $F_\rho$ is the fold above |
| `ntt` | $y_{j,\ell}=P_\ell(\alpha_j)$, using the production additive-transform domain, basis, and schedule |

## Baselines and candidate scope

GF scalar/unary baseline: production Flock. GF wide/dot baseline: production
F2Z. Fixed/butterfly baseline: F2Z's x86 fixed-scalar behavior, which currently
calls ordinary hardware multiplication. `Prepared` is separately labeled and
now uses PCLMUL on x86. The software-only helper is not the competitive baseline.

Prime, integer, wide-product and projection baselines are the same production
implementations used by the existing arithmetic suite. Primitive integer
add/sub/mul and setup-only cases are diagnostics. Candidate comparisons include
Flock's scalar product graphs, unroll/accumulator counts 1/2/4/8, packed x4
VPCLMUL, prepared constants, and existing integer-focus alternatives. Unsupported
packed kernels are omitted explicitly according to the frozen compiled feature
profile. The runner validates host support; it never silently substitutes
software for a declared hardware kernel.

The NTT `preserved_schedule` variant substitutes the experimental scalar
Karatsuba/Barrett kernel into a private Flock copy. Transform sources remain
byte-identical. Specialized packed/twiddle kernels remain production code and
can bypass scalar multiplication. This variant therefore measures **scalar
substitution only**, not an optimized replacement of every NTT arithmetic path.
Its result must not be attributed to packed-kernel integration. A separate
instrumented build checks actual scalar calls without contaminating timing:

```sh
python3 experiments/field-regressions/run.py --suite x86 --cpu-set 0 \
  --probe-ntt --out /tmp/ryzen-ntt-activation
```

`activation.json` records whether each transform actually exercised the scalar
substitution. Counting builds never emit timing samples and cannot pass the
performance gate.

## Run

All commands run from the repository root. Populate the pinned toolchain's
dependency cache first if necessary; campaign builds are offline. Use a new
output directory every time. Keep other compilation/benchmark jobs idle while
workers are measuring. The driver executes jobs sequentially and leaves the
machine's governor and boost settings unchanged.

```sh
# Inspect the exact local placement/workload matrix without running it.
python3 experiments/field-regressions/ryzen.py \
  --out /tmp/ryzen-explore --streaming --scaling --dry-run

# Development sweep: three processes, eight samples, 3 ms calibration.
python3 experiments/field-regressions/ryzen.py \
  --out /tmp/ryzen-explore --streaming --scaling

# Independent confirmation: frozen decisions, fresh seeds, five processes,
# 32 samples and 20 ms calibration; one predeclared retry if inconclusive.
python3 experiments/field-regressions/ryzen.py \
  --phase confirm --exploration /tmp/ryzen-explore \
  --out /tmp/ryzen-confirm --streaming --scaling
```

Single-core runs pin CPU 0 (96 MiB L3) and CPU 8 (32 MiB L3). Optional consumer
scaling runs use CPUs 0-7, 8-15, 0-15 and 0-31 (8/8/16/32 threads). The fused
arithmetic microkernels remain single-thread algorithms in those processes;
NTT and full-prover consumers are the parallel scaling evidence. Keep SMT
siblings idle for the single-core comparisons; the runner records placement and
load but does not reserve cores against other processes.

A narrow development run is useful when changing a kernel:

```sh
python3 experiments/field-regressions/run.py --suite x86 --cpu-set 0 \
  --runs 1 --samples 2 --calibration-ms 1 --no-retry \
  --cases x86_products/16,x86_dot/17,gf_fold_round/17,ntt/log8_lanes1 \
  --out /tmp/ryzen-smoke --target-dir /tmp/bitz-ryzen-target
```

Such a partial run cannot supply a complete confirmation selection or pass the
gate. A different `--flags` profile is a separate campaign; do not compare
candidate and baseline built with different profiles. The default is
`-C target-cpu=native`. No Intel or ARM timing is implied.

## Selection and reporting

`measurements.md` and `summary.json` retain production ratios, median/P95
pointwise confidence bounds, process medians, payload and allocations. JSON
also reports normalized ns/term, terms/s and logical payload GiB/s (not measured
DRAM bandwidth). `rankings.md/json` shows candidate rankings and paired
comparisons with the strongest challenger. Exact latency chains and batch
throughput are separate families.

Exploration emits `selection.json`, selecting per operation/size. The incumbent
is retained unless development evidence supports a faster nonregressing
candidate. Confirmation requires this selection, unchanged source hashes,
identical host/build/placement/thread configuration, and fresh process seeds.
Confirmation retains the frozen choice, its production baseline, its strongest
predeclared challenger, and any reset control; other alternatives remain in
the exploration archive. Wrappers that deliberately call an existing kernel
are labeled in `implementation_aliases`; selection names that underlying
kernel. Their wrapper measurements remain visible during exploration.
The selection is not a production dispatch table; actual dispatch thresholds
need implementation and neighboring-size validation before integration.

The gate rejects exploration, missing coverage, wrong affinity/backends,
changed artifacts, allocation increases, production regressions, and an
uncleared predeclared challenger. Production and challenger comparisons both
retain the 1% median/P95/process policy. A tie is reported as within 1%; the
campaign establishes best measured candidates among its declared comparisons,
not universal optimality. P95 describes timed-batch averages, not individual
operation tail latency. All improvements are host/workload/build specific.

Each x86 run preserves frozen source and executable archives, disassembly when
objdump is available, metadata, exact applicable variants, raw samples,
per-process host observations, and the selection/ranking records. Profiling or
hardware-counter collection should use a separate run; do not mix its overhead
into confirmation samples. `assembly.txt.gz` contains the frozen executable's
native disassembly for inspecting multiply/reduction/carry schedules.

## Focused x86 repairs

The `--scope candidate-repairs` matrix isolates the OOD, incremental NTT, and
public 3-by-7-limb polynomial-dot candidates from the latest audit. It covers
52 operation/size cases on each single-core placement and 16 on each scaling
placement: 168 cases in total with `--scaling`. OOD powers of two straddle both
dispatch cutoffs; NTT shapes straddle the serial/parallel cutoffs; polynomial
lengths include 15/16/17 and 1023/1024/1025 with dense, sparse, zero, alternating,
dense-prefix, and sparse-prefix inputs. The comparison is against production.

On x86, OOD uses 256-element tiles for small inputs, prepared equality products
for medium or single-thread inputs, and grouped parallel tiles for larger
inputs. NTT retains production for more than 32,768 elements, or for domains
of at least 4,096 points with multiple threads. Smaller NTTs stay serial to
avoid worker allocations. Those production retentions and OOD helper aliases
are recorded using the actual thread count; fallback wrappers cannot be
selected or counted as separate speedups. The public polynomial candidate
accumulates carryless-product diagonals in SIMD registers before combining
their low and high halves. A zero left-prefix is skipped before initializing
those registers, and all-zero batches return immediately. Its zero-skips retain
the public-input contract; the private-input kernel and ARM implementations are
unchanged.

```sh
python3 experiments/field-regressions/ryzen.py --scope candidate-repairs \
  --scaling --out /tmp/x86-candidate-repairs-explore
```

For a complete audit of the current branch, use `--scope comprehensive` with
`ryzen.py`. This adds the operation-metrics and optimization workloads, plus
the latest candidate-fix alternatives, to the original x86 matrix and repaired
cutoff neighbors. ARM selections are not imported. The native streaming matrix
has 101 families, 773 operation/size cases and 2,415 applicable variant cases per single-core
placement; each scaling placement has 16 consumer families and 86 cases.
The ARM-only GF(2^127) Karatsuba and polynomial-fold entry points are explicitly
listed in `unavailable_variants`; the production operation remains measured.
Operations with only one implementation are diagnostics, not measured speedups
or independent regression comparisons. Exploration screens all alternatives;
fresh confirmation is required for performance conclusions.

The GF grid baseline extracts the real `dense_grid_pass_slices` dispatch and
its helpers from production. The optional `eqf_grid_pass` hook only has an ARM
implementation; unwrapping it directly is invalid on x86. The extracted dispatch
uses production's generic fallback here. Its nine outputs and compacted prefixes
are checked against the existing independent field oracle on both architectures.

```sh
python3 experiments/field-regressions/ryzen.py --scope comprehensive \
  --streaming --scaling --out /tmp/x86-comprehensive-explore
```

`--scope regressions` covers the six families involved in the reported
slowdowns: GF products, single/two-pair GF rounds, full-width two-limb MAC,
prime dots and NTT. It includes both neighboring SIMD sizes (3/4/5) and
neighboring short-integer sizes (31/32/33). Single-core streaming adds one GF
product case. The resulting profile has 81 operation/size cases per single-core
placement and 35 per consumer-scaling placement.

The repairs use exact chunks plus a scalar tail for unrolled GF products,
and masked SIMD tails for mixed packed-product batches;
five-CLMUL Barrett reduction for the NTT scalar substitute; packed VPCLMUL
rounds with one final reduction per coefficient and a shared traversal for
two pairs; separate low-product and high cross-product integer accumulators;
and borrowing in the prime-dot adapter. The original materializing adapter
remains an allocating comparison control. Short integer batches retain the
production loop; sub-four-slot rounds retain the existing scalar kernels.
Every dispatch depends only on public lengths and compile-time ISA support.

The current revision also compares the upstream tiled NTT on this x86 host,
using the same standard basis, complete output check and reset copy as Flock.
It is an additional candidate; ARM selections are not imported. Allocation
audits use 64 untimed calls to cover periodic Rayon queue allocations, retaining
the maximum allocation count/bytes for one call and the existing limits.

```sh
python3 experiments/field-regressions/ryzen.py --scope regressions \
  --streaming --scaling --out /tmp/x86-repair-explore
python3 experiments/field-regressions/ryzen.py --scope regressions \
  --streaming --scaling --phase confirm --exploration /tmp/x86-repair-explore \
  --out /tmp/x86-repair-confirm
```

These remain experimental candidates. Passing this focused profile establishes
the recorded selected paths' performance on this host, not a promotion of every
alternative or an end-to-end prover speedup.

## Full prover consumers

```sh
python3 experiments/field-regressions/end_to_end.py \
  --out /tmp/ryzen-provers --scaling --dry-run
python3 experiments/field-regressions/end_to_end.py \
  --out /tmp/ryzen-provers --scaling
```

The driver freezes sources, builds all selected binaries before measurement,
and runs one configuration per worker. It covers F2Z u32-mod32/u128 proofs at
log sizes 15/20, split SHA256+ECDSA at 7/12 and security 100, and PCS shapes
13:7:1, 16:10:1, 7:8:32. Every bench verifies its proofs. Raw logs and structured
phase/proof records are retained; optional external prover backends are not
measured. Baseline characterization is the default: a faster microbenchmark
does not mean production is using it.

These existing full-prover benches require the native Perfetto trace processor.
Install it using the [official instructions](https://perfetto.dev/docs/analysis/trace-processor)
and set `PERFETTO_TRACE_PROCESSOR=/absolute/path/to/trace_processor_shell`.
The driver checks this dependency before building and archives its executable,
version and hash. Pure arithmetic and NTT campaigns do not need it.

After candidate integration, supply `--candidate-root` and
`--activation-evidence` (the integration-test record proving candidate paths
are exercised). Baseline/candidate workers alternate in reproducibly shuffled
order with identical configured inputs, security, flags, placement and threads.
The evidence is copied into the report, not independently certified by this
runner. Match deterministic transcript/proof bytes in the integration tests.
Full prover sampling uses five fresh processes by default and retains individual
records; it does not reuse the microbenchmark gate's batched-tail claim.

## Validation

The implementation's local validation record is in
[`results/ryzen-x86-validation/README.md`](results/ryzen-x86-validation/README.md).

```sh
python3 -m unittest discover -s experiments/field-regressions -p 'test_*.py'
RUSTFLAGS='-C target-cpu=native' cargo check --offline \
  --manifest-path experiments/field-regressions/Cargo.toml \
  --features arithmetic-campaign
```

Every worker performs the existing independent GF basis/random/codec/inverse
checks, plus x86 candidate/tail checks. Timed candidates check their outputs
before measurement. Montgomery and full-width integer cases use independent
BigUint/BigInt arithmetic. Wide-product validation keeps length/bound/error and
output-overwrite tests. Consumer checks compare coefficients and complete
modified arrays, not only a scalar checksum. These are arithmetic correctness
and performance experiments, not constant-time certification.
