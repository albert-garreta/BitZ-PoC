Falcon grinding/configuration experiments — 2026-10-09

Status: screening and fresh-input confirmation complete. None of the four
selected schedules established a prove+commit speedup against the same-binary
baseline: all four paired 95% intervals include no change. Mean paired time
reductions were 0.06%, 0.17%, 0.20%, and 0.49%. Query tuning did reduce payload
size. The existing security budget was retained. This is an isolated experiment;
its source changes have not been promoted to production.

Purpose and scope
-----------------
Test whether changing grinding allocation and PCS query counts improves latency
while retaining the existing 128-bit proof-security target and composed error
budget. Each input batch contains 1024 signatures. The four workloads are
Falcon-512 arithmetic, Falcon-1024 arithmetic, Falcon-512 full, and Falcon-1024
full. Arithmetic benchmarks use 8 workers and full benchmarks use 16 workers,
the best counts in the preceding 1/2/4/8/16-worker baseline campaign.

Earlier instrumented profiles measured grinding at about 4–6% of prove-only
time at those worker counts: arithmetic-512 3.74 ms (5.83%), arithmetic-1024
4.84 ms (4.34%), full-512 17.31 ms (5.82%), and full-1024 22.50 ms (4.00%).
Those were seed-42 diagnostic profiles, not the latency results of this
experiment. They indicate limited headroom from grinding alone. Query changes
can also affect PCS opening, verification, and proof payload size.
Source: ../falcon-grinding-schedule-study-20261009/profile-analysis.json and its
raw profiles.

Configurations screened
-----------------------
original: saved unmodified binary from the preceding d9b13bdb4 campaign.
baseline: experimental binary with all experimental controls disabled.
global: include prime-field stages in the shared grinding-budget allocation.
weighted: global allocation plus corrected grinding-boundary work counts and
  the first measured search-cost curves, calibrated from a Rayon worker.
queries124: global allocation plus a 124-bit raw PCS query target.
queries120: global allocation plus a 120-bit raw PCS query target.
queries116: global allocation plus a 116-bit raw PCS query target.
weighted_queries120: weighted allocation plus the 120-bit raw query target.
weighted_external: weighted allocation using the second cost calibration,
  invoked from the external main thread as in the actual prover drivers.
weighted_external_queries120: weighted_external plus the 120-bit raw query
  target.

The 124/120/116 labels are raw query targets, not final proof-security targets.
Additional query grinding compensates for the reduced number of queries.
These variants also include global allocation; a comparison against baseline
measures their combined effect. Rate 1/2 and initial folding parameter 4 remain
fixed. The weighted allocator is a heuristic search, not a demonstrated exact
global optimum.

The corrected work model includes the bridge's root boundary and uses
2 + 2 * PCS_block_count outer-opening boundaries at target 128. These are cost
weights; they do not change the security error numerators.

Measurement method
------------------
Hardware: Ryzen 9 9950X3D. Native release build, opt-level 3, fat LTO, one codegen
unit, RUSTFLAGS=-C target-cpu=native. Saved experimental binaries are reused
across all profiles, with an additional saved original-binary control.

Screening plan: ten profiles, seeds 42/43/44, all four workloads. Profile and
workload order is deterministically shuffled. Each execution has one excluded
warmup and seven measured repetitions. Input digests must agree across profiles
for a matched workload/seed. Every warmup and measured proof is verified, and
the execution checks security, proof-digest consistency, and reported worker
affinity before accepting a result.

Main thread is pinned to CPU 6. Worker order is
6,7,4,5,2,3,0,1,14,15,12,13,10,11,8,9, truncated to the requested count.
The runner executes on CPU 31. Before a run, selected workers and their SMT
siblings must be below 5% busy in an idle sample. During an accepted run, every
unused SMT sibling must be below 2% busy. Rejected raw attempts are retained and
excluded without considering their measured speed.

The initial three-repeat screening was superseded uniformly by seven repeats
after short-interval contention rejections; see screen-method-update.json.
The retry cap later increased from 4 to 30 without changing the 2% acceptance
criterion; see retry-method-update.json. The pre-run idle-check limit increased
from 15 to 300 one-second attempts, retaining the same less-than-5% idle
criterion and less-than-2% in-run sibling criterion. Nineteen screening cases
that overlapped a known external build were excluded and rerun, including cases
that had passed the sibling-utilization check. Their identifiers are preserved
in external-build-exclusions.json. Confirmation also has an external-process
monitor polling every five seconds, recording observations in
external-process-events.json. Its polling interval can miss short-lived work;
it does not establish perfect isolation. CPU tick granularity and unobserved
external activity remain limitations of this noise control.

For each seed, the summary uses the median of the seven measured repetitions.
Seeds, rather than repeated deterministic proofs, are the independent sampling
unit. The analysis computes paired ratios and seed-resampled bootstrap
intervals. Three screening seeds provide weak evidence for small differences;
fresh inputs are needed to confirm selected candidates.

Screening completed 120 accepted executions and 960 verified proofs, including
warmups. Candidate schedules were frozen in selection.json before holdout.
Confirmation uses fresh seeds 45 through 54 and compares each selected candidate
with both baseline and original controls, with deterministically shuffled
workload/profile order (confirm.py). No curves or schedules are refitted using
holdout measurements.

Confirmation completed all 120 planned executions and 960 verified proofs.
Together with screening, the accepted timing dataset contains 240 executions,
1,680 measured proofs and 240 warmups: 1,920 verified proofs in total. There are
13 distinct input digests per workload across seeds 42 through 54. Original and
baseline proof digests and payload sizes match in all 52 workload/seed pairs.

The final audit checked 619 source-manifest entries, four binary hashes, cost
and execution fingerprints, the frozen screening summary, raw medians, input
identity, security, and affinity/noise criteria. No accepted run overlaps the
known external-build interval using conservative file-mtime brackets. It passed
with a flag for external-process observations; see the limitation below and
external-monitor-review.json. The observed minimum composed accounting was
128.093109501 bits. Validation passed 157 test executions in 53 invocations;
repeated tests under different configurations count separately.

Excluded records are counted separately: screening discarded 80 executions /
640 verified proofs; confirmation discarded 35 / 280; superseded short screening
retains 7 / 28. Smoke and corpus preparation contributed 8 and 48 additional
verified proofs for correctness only. None of these excluded/correctness-only
records contributes to the accepted performance summaries. See final-audit.json.

Metrics
-------
Prove measures prepared.prove. Prove+commit includes checked witness derivation,
packing/commitment, and proving. It excludes reusable preparation, generation
of signature inputs, and separate native Falcon verification. Full commit
timing also includes cloning the committed statement, as in its existing driver.
Proof verification is timed separately. Proof bytes are counted payload bytes,
including the 32-byte source root, not a measured serialized wire format.

Security and correctness evidence
---------------------------------
The allocator preserves the existing composed algebraic/IOP error budget:
  sum(error terms) <= (15/16) * 2^-128,
corresponding to at least 128 + log2(16/15), approximately 128.093109, bits in
that accounting model. Native Flock grinding floors and the 32-bit difficulty
cap remain enforced. Prime sampling and native-ring terms remain included.
The actual prepared difficulties and PCS configuration are bound into the
existing transcript digest and used consistently by prover and verifier.

This retains the repository's existing computational grinding/soundness model;
successful proofs and accounting tests are not a new cryptographic proof of
the entire construction. The algebraic/IOP ledger is separate from the hash
security assumption.

Validation logs show successful allocator/query tests, configuration and nonce
mutation rejection, and composed-budget checks for the tested configurations.
Weighted schedules were checked for cost-model thread classes 1/2/4/8/16,
including both external-cost profiles. These are schedule-validation classes;
this experiment's end-to-end timing scope remains 8 arithmetic / 16 full.
With experimental controls disabled, smoke tests matched the saved original
proof digests in all four workloads. Smoke timings are not used as results.

Arithmetic budget tests independently reconstruct UDR fold/query bounds with
rational arithmetic for both degrees and every power-of-two capacity through
1024. Full composition tests cover 14 representative batch sizes, exactly
aggregate the represented bounds, and check compensated query difficulty.
Their PCS inputs are floating-point raw error bounds converted to rationals,
so those tests are not an independent rational derivation of PCS soundness.
The full exact/mutation unit tests use the existing Falcon-1024 test instance;
full Falcon-512 is covered by actual verified benchmark proofs, not the same
unit-test suite. See validation/summary.json and validation-external/summary.json.

Cost-model qualification
------------------------
The first calibration ran grinders inside pool.install. Actual prover drivers
call them from the non-Rayon main thread, where Rayon broadcast uses a blocking
latch rather than a worker's stealing latch. The second calibration reproduces
that external entry, global pool, and main/worker CPU arrangement. It leaves the
first curves intact, so the two weighted variants remain distinguishable.

The external probe recorded 104,576 measured searches across thread classes
1/2/4/8/16; nonces were checked, with matching minimum nonces across thread
counts. Cost fits estimate expected search time from actual nonce lengths.
They preserve parallel-dispatch threshold dips; bits 25–32 are extrapolated
from measured high-bit throughput. Repeated isolated searches still cannot
reproduce every cache, clock, sleep, and scheduling state within a full proof.
End-to-end holdout measurements decide performance, not the cost objective.
See costs-external/README.txt and costs-external/final-provenance.json.

The two arithmetic winners use the initial worker-entry cost calibration.
The caller-context mismatch limits that cost model, but the resulting fixed
schedules remain valid security-checked candidates. Their actual performance
must be assessed by the same holdout as the external-calibration full winners.
A model with more faithful isolated-call timing need not select the fastest
whole-proof schedule. No speedup is inferred from calibration quality alone.

Some named configurations produce identical proofs. Across all three screening
seeds, full-512 global and weighted_external have identical proof digests;
queries120 and weighted_external_queries120 also match for both full degrees.
Their timing differences are repeated measurements of the same resulting
proofs, not evidence of distinct schedule improvements. Baseline and original
proof digests match for every screened workload and seed. The fresh holdout
tested the nominated full-512 configuration on independent inputs.

External-process limitation

The monitor recorded events, so this was not demonstrated perfect machine
isolation. Two observations with unresolved working directories may correspond
to exiting benchmark processes; that attribution is uncertain. A third process
had an external working directory and was observed after the last accepted run.
The five-second polling interval permits a short possible overlap with the
last arithmetic-1024 original-control run. Review and sensitivity calculations
are recorded in external-monitor-review.json. Retain this limitation when
interpreting sub-percent differences, including the secondary binary comparison.

Conservative sensitivity checks preserve the conclusion. Excluding full-1024
seeds 50 and 53 gives a candidate/baseline total ratio of 0.99598 with 95%
interval [0.98991, 1.00176] across eight inputs. Excluding arithmetic-1024 seed
54 gives a candidate/original total ratio of 1.00067 [0.99626, 1.00423] across
nine inputs. Both still include no change. The last external-process observation
does not affect the arithmetic-1024 candidate/baseline comparison: those two
runs had completed before the possible overlap window. See sensitivity-summary.json.

Payload and preparation tradeoffs

The arithmetic-1024 weighted_queries120 holdout payload averaged 350,348 bytes
versus baseline 363,053 bytes, a 3.50% reduction. Its prove+commit and verification
changes remain statistically inconclusive. Other selected candidates changed
mean payload sizes by less than 0.1%.

The queries116 screening variant reduced mean payload sizes by about 6.1%,
5.0%, 4.6%, and 3.7% for arithmetic-512, arithmetic-1024, full-512, and full-1024,
respectively, with near-flat total-time point estimates. This variant was not
selected for fresh holdout; those size/latency observations remain screening
evidence, not a confirmed performance recommendation.

Reusable preparation is excluded from the timed prove+commit metric. Recorded
preparation means from confirmation were:

Workload            Baseline ms  Candidate ms   Added ms
arithmetic-512            0.254         0.651      0.396
arithmetic-1024           0.232         0.833      0.601
full-512                  4.782         5.239      0.457
full-1024                 3.117         3.584      0.467

Weighted preparation adds roughly 0.4–0.6 ms in this experimental implementation.
That cost matters if preparation is repeated for each proof, and is amortized
when the prepared configuration is reused. It is not included in the apparent
small prove+commit reductions above. Source: preparation-summary.json.

Conclusion

The experiments do not justify promoting a grinding-schedule change for prover
latency. Four fresh-input total-time comparisons were inconclusive, and the
observed grinding share already limits the benefit available from this area.
Query-count tuning offers a demonstrated payload-size tradeoff while preserving
the existing security budget: the selected arithmetic-1024 query variant kept
a roughly 3.5% smaller payload in holdout without an established latency gain.
Further latency work should target the larger non-grinding stages. If smaller
proofs are the priority, query tuning merits targeted follow-up with the same
security accounting and independent-input validation. No production change was
adopted or pushed as part of these experiments.
