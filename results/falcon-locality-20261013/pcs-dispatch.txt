What the existing measurements establish

baseline-profiles/assessment.txt and pcs-summary.json report median induced-
basis time 0.46 ms / 0.61 ms for Falcon512/1024. These are nine measured diagnostic
proofs per degree at 12 physical workers, three seeds, with one excluded warmup
and three measured proofs per seed. The six processes used the frozen baseline
binary bf303cb59a2e6830f0beb97670bd693aaef0d22fd5ad54bb7304696e0c850511.
All 24 proofs, including warmups, were validated by the profiling campaign.

The timer aggregates initial sparse NTT and all recursive dense calls. It does
not establish which level, allocation, arithmetic loop, or reduction dominates.
The text values are rounded to 0.01 ms, tracing perturbs latency, and nested
timings must not be added as independent costs. The 0.59 ms / 0.56 ms unattributed
Ligerito residual is separate unscoped work, not evidence of NTT overhead.

Concrete follow-up hypothesis; not implemented in this campaign

At vendor/flock-mod/crates/flock-core/src/pcs/ligerito.rs:2422, the sparse
transpose uses a HashMap and one 256-element Vec per active window; :2432
collects and processes those windows, and :2458 allocates a full-domain buffer
and copies the processed windows into it before the dense sweeps at:2465.

A bounded proof-preserving experiment is to allocate that full-domain buffer
once, scatter the query weights while marking active windows, and process
active disjoint 256-element chunks directly in parallel. Keep the same window
index/twiddle calculation and within-window butterfly order. This removes the
HashMap, per-window allocations, and densification copy while retaining sparse
arithmetic for inactive windows. It changes neither query order and weights,
enforced sum, resulting basis, nor transcript/grinding operations.

Concrete bounds: the initial domains have 2^14 / 2^15 field elements, so the full
buffers are 256 KiB / 512 KiB and there are 64/128 possible 256-element windows. For
309 distinct query positions the number of active windows is at least 2 and
at most 64/128. Actual occupancy was not recorded; many active windows are a
plausible expectation, not an observed fact. Existing sparse-window storage can
occupy up to one additional full domain alongside the eventual output buffer.
The proposed active-window metadata would be only 64/128 flags plus any task
index list. Its latency benefit remains unmeasured and may be small.

Dense recursion is a secondary possible target: :2140 builds worker-local
accumulators and temporary bases and then reduces accumulators serially. The
largest recursive accumulator is 16 KiB / 32 KiB per worker, or 192 KiB / 384 KiB across
12 workers. Parallel coefficient reduction or direct accumulation could save
traffic, but the aggregate timer cannot justify prioritizing this over the
initial NTT path. Introducing sparse NTT itself would not be a new optimization.

Recommendation: retain the existing PCS code in the current locality campaign.
Consider the direct full-buffer sparse transpose as a separate small experiment
with per-level diagnostics and unchanged-proof validation before qualification.
No PCS speedup is established by this assessment.
