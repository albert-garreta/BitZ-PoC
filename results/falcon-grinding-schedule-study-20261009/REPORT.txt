Falcon grinding schedule study
Source: d9b13bdb43cd2d3a0901b44f0939293f234661b5
Batch 1024; 128-bit target; Ryzen 9 9950X3D.
Diagnostic profiles: 1/8/16 threads, one warmup plus three measured trials each; all 48 proofs verified.

Grinding share at previously fastest worker counts (instrumented prove-only):
  arithmetic 1024, 8 threads: 4.84 ms, 4.34%
  arithmetic 512, 8 threads: 3.74 ms, 5.83%
  full 1024, 16 threads: 22.50 ms, 4.00%
  full 512, 16 threads: 17.31 ms, 5.82%

Schedule candidates (modeled hash reductions, not measured wall-time improvements):
  Include prime groups, arithmetic 512: 0.80% fewer expected hashes; ledger 128.093298 bits.
  Include prime groups, arithmetic 1024: 9.82% fewer expected hashes; ledger 128.093177 bits.
  Include prime groups, full 512: 8.61% fewer expected hashes; ledger 128.093110 bits.
  Include prime groups, full 1024: 10.39% fewer expected hashes; ledger 128.093238 bits.

Recommendations:
  1. Measure cost per difficulty/thread class and use accurate boundary counts. The current hash-count model misses dispatch overhead and undercounts outer opening sites (full512: 31 modeled, 60 recorded).
  2. Include prime-field stages in the composed allocation. Preserve a fixed, verifier-bound schedule and the existing 15/16 budget.
  3. Sweep PCS query counts jointly with query grinding. The 120-bit raw query target candidates retain >=128.09 composed bits in the model; full Falcon query counts fall 1061 to 994 across levels while modeled hashes increase about 4% relative to the global-allocation 128-query-target baseline. End-to-end measurements are necessary.
  4. Per-boundary raw-error allocation is a further possible improvement; requires independent degree accounting for each adaptive boundary.

Low-value/unsupported shortcuts:
  Pairwise integer schedule exchanges found <0.05% model improvements in these four cases.
  No native Flock minimum is binding in the current four baseline schedules.
  Changing initial_k from 4 to 5/6 would require opening-layout integration; it is not just a profile swap.
  Changing rate 1/2 to 1/4 increases the modeled UDR fold work and doubles codeword expansion; do not assume it helps grinding.
  Current composed margin is about 0.093 bits; maintain it for apples-to-apples tuning.

Separate finding: src/piop/spartan/falcon1024_algebraic/arithmetic.rs:409 enables optimized binding only at 8 workers (batches 256..1024) and 1 worker (batch1024). 16 workers uses Legacy. This is relevant to the arithmetic 8-to-16 thread slowdown but outside grinding schedule scope.

Limitations:
  Same input seed 42; repeated trials characterize timing, not nonce-distribution variability.
  Instrumentation adds overhead; use original uninstrumented campaign for latency comparisons.
  Opening work weight retains current source estimate; observed block counts are higher.
  Initial-k survey does not preserve the fixed 16-lane opening geometry and is not a drop-in Falcon configuration.
  Query tradeoff sweep includes prime groups in optimization; its 128-query-target case is the comparison baseline.
