Conclusion
  Both targeted baseline paths perform actual serial eager initialization.
  Coordinate tables use malloc followed by inline stores of zero; the first
  word-fold table uses malloc followed by memset and one final vector store.
  Neither target table already obtains its storage through calloc. This is
  established from generated instructions, not inferred from vec! syntax.
  These instructions establish a cost mechanism, not the savings achievable
  by any candidate. Allocation, first-touch faults, later writes and page
  placement still need measurement; lazy-zero allocation can move physical
  zeroing/fault work to worker writes rather than eliminate it.

      Computes batch * 22528 = batch * 1024 * 22 bytes per coordinate table.
    0x35b29e: call malloc through GOT 0x594cc8 (first table)
    0x35b2e0..0x35b35d: unrolled serial zero loop, eight entries per iteration
    0x35b370..0x35b39b: zero the remaining entries
    0x35b3b2: call malloc through GOT 0x594cc8 (second table)
    0x35b470..0x35b4ee: equivalent eight-entry zero loop
    0x35b500..0x35b52b: zero the remaining entries

  The per-entry store pattern is:
    vmovdqu %xmm0,(destination)       # 16 zero bytes
    movq $0x0,0xe(destination)       # 8 zero bytes, overlapping two bytes
  The loop advances 0xb0 = 176 = 8*22 bytes. These instructions write all
  canonical-zero coordinates before the recurrence workers overwrite them.
  There is no memset or calloc call for either large coordinate vector.
  The smaller batch-sized target vector also has malloc plus inline zeroing
  (malloc at 0x35b544; zero loop at 0x35b590).

  N=512 follows the same implementation:
    0x2042d4 / 0x204301: imul $0x2c00 (batch * 512 * 22 bytes)
    first malloc 0x20433e; main zero loop 0x204380..0x2043fd
    second malloc 0x204452; main zero loop 0x204510..0x20458e

  For batch 1024, the two coordinate vectors cover 22 MiB (N512) or 44 MiB
  (N1024) of distinct storage. The overlapping store widths issue 24 bytes per
  22-byte entry; this is not a claim about measured DRAM traffic.

Allocator routing
  __rust_alloc is at 0x12fe50, size 0x4d.
  For alignment <=16 and size >= alignment, it tail-calls malloc at 0x12fe67.
  Thus the first-fold alignment-8 allocation above uses malloc, not calloc.

  __rust_alloc_zeroed is at 0x12ff50, size 0x76.
  For ordinary size >= alignment, its path at 0x12ff98..0x12ffa7 tail-calls
  calloc(size,1), through GOT 0x594d10. Its alternate aligned path uses
  posix_memalign then memset. Presence of this allocator in the binary does
  not mean baseline coordinate/word tables call it; their sites above do not.

  Baseline:

    Second __rust_alloc at 0x4219e3; zero loop at 0x421a90..0x421b0e.
    The serial zeroing baseline remains available in the candidate.

  Zeroed:
    First table calls calloc(size,1) directly at 0x421843.
    Second table calls __rust_alloc_zeroed at 0x421a3b with alignment 2.
    For these nonempty 22-byte-element allocations, __rust_alloc_zeroed
    routes to calloc at 0x1323b7. Neither table has an additional caller-side
    fill after allocation. N512 calls are 0x320fc3 and 0x3211bb.
    This verifies allocation lowering; libc/OS can still perform zeroing or
    page-fault work, depending on allocation size and reuse history.

  Direct:
    First table malloc at 0x421762, then metadata-only path to 0x42193b.
    Second __rust_alloc at 0x421976 with alignment 2, then metadata-only
    path 0x421e87 -> 0x421dde -> return. __rust_alloc routes to malloc.
    The vector lengths are stored as zero. There is no preinitialization
    loop, memset, or calloc on this path. N512 calls are 0x320ee2 and
    0x3210f6. Subsequent parallel recurrence writers initialize the slots.

  Warm reuse:
    Checkout clones the Arc and takes the mutex at 0x42168a..0x4216a8;
    cached vector metadata is moved out, and mutex unlock is 0x421716
    before output-buffer processing.
    At 0x421c8c..0x421c92, requested first length minus existing length
    branches to 0x4217aa when no growth is needed.
    At 0x4217af..0x4217ba, the same condition for the second vector branches
    to 0x421dd4, then metadata-only return at 0x421dde.
    Thus fixed-shape initialized cache hits do not allocate or zero the
    coordinate outputs. Empty cache/cold reuse and larger requested lengths
    enter reserve/zero-suffix paths. No claim of lock-free operation is made.

Interpretation
  The candidate implements the intended memory-write experiments in machine
  code: calloc for zeroed coordinates, allocation without pre-fill for direct
  coordinates and direct word-fold outputs, and no output allocation/pre-fill
  on fixed-shape warm coordinate cache hits. Baseline branches retain eager
  initialization. Timing and end-to-end qualification are separate evidence;
  this inspection alone does not establish a speedup.
